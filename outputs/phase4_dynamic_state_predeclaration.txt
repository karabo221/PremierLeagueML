4. DYNAMIC STATE DEFINITION  (frozen)
===============================================================================

STATE SOURCE
    Elo state      : Phase 2 Elo walk, date-batched, class-A constants only.
    DC state       : Phase 2 fit_window(), refitted before every distinct test
                     date on all matches with date STRICTLY < that date
                     (the existing dc_walkforward regime).

D2 DESIGN-MATRIX FEATURES  (5, differences and scalars only)

    rel_elo_diff          = home_elo_before + HOME_ADVANTAGE - away_elo_before
                            NOTE: verified numerically that Phase 2's
                            elo_diff column ALREADY includes the +60 home
                            advantage. It is used as-is, not re-added.

    rel_attack_diff       = log(A_home) - log(A_away)
    rel_defence_diff      = log(D_away) - log(D_home)
                            signed so that positive favours the home side

    expected_total_goals  = lambda_home + lambda_away
    log_lambda_ratio      = log(lambda_home) - log(lambda_away)

NO LEVELS-PLUS-DIFFERENCE REDUNDANCY
    home_elo_before and away_elo_before are NOT in the design matrix.
    lambda_home and lambda_away are NOT both in the design matrix.
    Only differences and the two scalars above enter D2.

JUSTIFICATION OF THIS EXACT REPRESENTATION (required to be fixed in advance)
    lambda_home = A_home * D_away * H
    lambda_away = A_away * D_home
    Therefore
        log_lambda_ratio = rel_attack_diff + rel_defence_diff + log H
    and (expected_total_goals, log_lambda_ratio) jointly determine
    (lambda_home, lambda_away) exactly.

    expected_total_goals is included because attack and defence differences
    alone cannot represent the scoring ENVIRONMENT. Total expected goals
    drives draw probability independently of the mismatch: two fixtures with
    identical strength difference but different total goals have materially
    different draw mass. Omitting it would make D2 underperform direct DC for
    a reason unrelated to dynamic state, confounding the very comparison this
    experiment exists to make.

    log_lambda_ratio is retained alongside the attack/defence decomposition
    despite partial overlap. The explicit reason: H is refitted per window and
    therefore varies, so the identity above is not a fixed linear relation and
    the ratio is not recoverable from the two differences alone. The
    decomposition says WHERE the ratio comes from; the ratio says what it is.

RETAINED INTERNALLY FOR DIAGNOSTICS ONLY (never in the D2 design matrix)
    lambda_home, lambda_away, A_home, A_away, D_home, D_away, rho, H,
    home_elo_before, away_elo_before
    Written to outputs/phase4_dynamic_state_state_history.csv.

UPDATE ORDER  (binding, per the brief)
    for each date T in chronological order:
        1. obtain state strictly before T
        2. construct features for every match on T from that state
        3. standardise using training-fitted scaler only
        4. predict
        5. record prediction
        6. observe results of all matches on T
        7. update state with the whole date's results
    Never update before predicting. Never let a match influence itself.
    Never let a same-day match influence another same-day match.

PROMOTED / RETURNING TEAMS
    Elo : 1500 flat for new_to_dataset, returning_after_absence and the
          2021-22 baseline cohort. Continuing teams regress to
          1500 + (r - 1500) * 0.75.
    DC  : NEUTRAL_STRENGTH = 1.0 for any team absent from the fitting window.
    Both are the existing validated Phase 2 rules and are NOT re-derived.
    The treatments DIFFER between Elo and DC and this is reported, not hidden.
    Affected-row counts are reported per fold.
    No Championship priors are introduced.

===============================================================================
6. STANDARDISATION  (frozen)
===============================================================================

Every continuous feature is standardised (zero mean, unit variance) using
TRAINING ROWS ONLY for the fit in question:
    - outer-fold model fit  -> scaler fitted on that outer fold's training rows
    - inner-CV fit          -> scaler fitted on that inner fold's training rows
The fitted scaler is then applied unchanged to validation / test rows.

This matters because the feature scales differ by orders of magnitude
(Elo ~1500, DC strengths ~1.0, goal counts ~0-100). Standardising first also
makes the L2 penalty comparable across rungs, which is required for the
per-rung lambda selection to be fair.

Boolean and indicator columns are passed through unstandardised.
Categorical columns are one-hot encoded with categories fitted on training
rows only; categories unseen in training map to all-zero.
Missing values are imputed with the TRAINING-fold median, fitted per fold.

Proven by DS13 and DS6.


===============================================================================
7. INNER VALIDATION  (frozen)
===============================================================================

PROTOCOL: expanding-window, blocked by gameweek. No random K-fold anywhere.

    Inner folds        : 4
    Block definition   : contiguous (season, matchweek) blocks of the outer
                         training rows, in chronological order.
    Construction       : the training rows are split into 5 contiguous
                         chronological blocks of approximately equal match
                         count. Inner fold i (i = 1..4) trains on blocks
                         1..i and validates on block i+1.
    Constraint         : every validation date must be STRICTLY later than
                         every training date in that inner fold. Asserted
                         programmatically (DS12), not assumed.

WHY BLOCKED RATHER THAN A SINGLE CHRONOLOGICAL HOLDOUT
    Fold 1 trains on 380 matches. A single 80/20 chronological holdout leaves
    ~76 matches to select lambda from, which is noisy enough to select a badly
    wrong value. Four expanding blocks pool roughly 300 validation matches
    across the inner folds while preserving strict temporal ordering.

Selection statistic: mean validation log loss pooled across the 4 inner folds.
Tie-break: smallest lambda among ties (declared in advance).

9. STATISTICAL COMPARISON  (frozen)
===============================================================================

PRIMARY DECISION METRIC : log loss
SECONDARY               : RPS
DIAGNOSTIC              : Brier
DESCRIPTIVE ONLY        : accuracy, balanced accuracy, macro F1
    Descriptive metrics may NOT decide any gate.

PAIRED BOOTSTRAP - required on D2-D1, D3-D2, D4-D3
    Both members of each comparison score the IDENTICAL 1,520 outer-test
    matches, so the comparison is paired and the per-match loss difference is
    the unit of analysis.

    Resamples   : 10,000
    Seed        : 20260831
    Resampling  : block resampling by (test_season, matchweek) - 152 blocks.
                  Matches within a fixture round share opponents and calendar
                  conditions and are not independent draws.
    Interval    : 95% percentile
    Reported for: log loss, RPS, Brier

    The procedure is NOT altered after seeing results.

DECISION RULE - a block demonstrates incremental value only when ALL hold:
    1. the point estimate improves log loss in the expected direction, AND
    2. the 95% paired bootstrap CI on log loss excludes zero, AND
    3. RPS is directionally consistent with log loss.

    If any condition fails, the verdict is
        "DID NOT DEMONSTRATE INCREMENTAL VALUE"
    NOT "useless". The distinction is binding on the report's language.

DECLARED POWER NOTE
    Measured on this project's existing outputs, the block-bootstrap standard
    error of a paired per-match log-loss difference is approximately 0.0014 at
    n = 1,140. At n = 1,520 the corresponding minimum detectable effect is
    approximately 0.0034 log loss at alpha 0.05 with 80% power.
    Effects smaller than that cannot be resolved by this design. A null
    verdict is therefore evidence of "not resolvable at this sample size", not
    evidence of absence. This is declared in advance so that null results are
    interpretable rather than disappointing.

10. LEAKAGE AND INTEGRITY TESTS  (frozen)
===============================================================================

    DS1   current-match result perturbation: prediction for T unchanged;
          earlier predictions unchanged; later predictions MAY change
    DS2   future-result perturbation: prediction for T unchanged
    DS3   same-day perturbation: prediction for T unchanged
    DS4   chronological state assertion: state timestamp strictly < match date
    DS5   fold isolation: corrupt outer-test results; training state and
          selected parameters unchanged
    DS6   training/test separation: outer-test rows never enter fitting or
          preprocessing
    DS7   reproducibility: two complete runs identical within tolerance
    DS8   state-update positive control: a valid historical result DOES alter
          an appropriate later state
    DS9   static-vs-dynamic: state genuinely changes through a season
    DS10  raw data integrity: no writes under data/raw/
    DS11  Phase 2 equivalence (see section 11)
    DS12  inner-validation leakage: every lambda selection uses training-only
          rows and every validation date is strictly after its training dates
    DS13  scaler leakage: corrupt outer-test feature magnitudes; selected
          model/scaler parameters for earlier folds unchanged
    DS14  hyperparameter perturbation: corrupt outer-test results/features;
          selected lambda for that outer fold unchanged
    DS15  Elo global-walk equivalence: per-fold re-walk reproduces the global
          walk element-wise (section 2)

EVERY test carries BOTH a positive control and a null control.
    Null control     : rebuild with zero perturbation, assert zero differences.
    Positive control : perturb data that SHOULD move the quantity, assert it
                       moves.
    Rationale: a builder that ignored its input entirely would pass every
    negative test trivially. Phase 1 Instrument 5 hit exactly this failure -
    12,822 spurious "changes" from comparing a CSV-loaded baseline against an
    in-memory rebuild, caught only by the null control.
